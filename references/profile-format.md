# 私有资料 JSON 教程

## 它是什么，为什么需要

这份文件是你确认过的事实清单，供 agent 阅读，不是自动执行脚本。它与网站不同：网站可能把论文放在“作品”下，也可能不支持某类奖项，agent 必须按实际字段判断，而不是修改事实去迁就选项。

本项目没有强制统一的 profile schema，也没有 JSON 到任意网站的通用自动映射器。已有 JSON 可以沿用；字段含义不清、来源冲突或资料缺项时，应先确认。本项目辅助脚本接受的是 agent 生成的计划与快照，不直接校验整份个人 JSON。

## 文件位置和加载顺序

把 [虚构示例](../examples/autofill-profile.example.json) 复制到公开仓库之外的工作目录，例如 `job-applications/private/autofill-profile.json`，替换示例记录并自行核对后设置 `example_only: false`。

查找顺序与 SKILL.md 一致：用户明确路径 → 宿主可见的 `JOB_APPLICATION_PROFILE` → 当前任务目录的 `private/autofill-profile.json`。找不到就询问位置，不搜索无关个人目录。环境变量是 agent 的读取约定，不是 Python 脚本的自动配置。

`example_only` 是给 agent 阅读的声明，不是可执行保护。只有关掉标记、却仍保留虚构经历，不能算可用于投递的个人资料。

## 建议的顶层分类

| 字段 | 内容 | 注意事项 |
|---|---|---|
| `basic` | 姓名、愿意提供的常规联系方式等 | 不包含证件号、密码或令牌 |
| `education` | 每段教育经历 | 学校、专业、学位、起止日期分别按来源记录 |
| `internships` / `employment` | 实习或工作经历 | 两种命名均可，明确身份和类别；不要重复同一经历 |
| `projects` | 项目与个人贡献 | 区分个人工作与团队结果 |
| `research` | 论文、研究成果等 | 每项保留真实类型、作者身份和当前状态；专利不可填成论文 |
| `competitions` | 赛事经历 | 保留真实赛事名称与范围 |
| `awards` | 获奖经历 | 与竞赛属于同一事件时可关联，不能虚构成两项独立成果 |
| `campus` | 校园组织或任职 | 任职、职责和日期按事实填写 |
| `skills` / `languages` | 技能、语言与证书 | 不把自评熟练程度改写成认证 |
| `field_metadata` | 缺失、确认无、不适用等状态 | 解释具体字段或整个类别的语义 |
| `autofill_policy` | 缺项、敏感字段等处理偏好 | 不授予浏览器写入或提交权限 |
| `presentation_policy` | 排序、压缩和排除偏好 | 不覆盖事实，不省略网站明确要求的全量信息 |

可以增加附件索引、专利等实际需要的类别。原始材料有新类别时不要因为模板没有就忽略。空类别应明确是尚未整理还是确实没有。

## 每条经历怎样写

推荐字段如下；未确认的信息用 `null`，不为了凑字段编造值：

| 字段 | 含义 |
|---|---|
| `record_id` | 本地唯一且稳定的标识，例如 `project-001`；更新内容时不随意换 ID |
| `name` / `title` | 真实名称 |
| `start_date` / `end_date` | 按实际精度写 YYYY、YYYY-MM 或 YYYY-MM-DD |
| `role` | 你的实际身份 |
| `description` | 可直接用于网申的事实正文 |
| `responsibilities` / `achievements` | 需要分开呈现的职责与成果 |
| `source` | 你确认该事实的来源，可以是本地材料路径及条目，或有日期的本人确认 |

以下内容全部虚构，只说明字段关系：

```json
{
  "record_id": "project-example-002",
  "name": "虚构示例：校园借阅工具",
  "start_date": "2023-03",
  "end_date": "2023-06",
  "role": "开发成员",
  "description": "实现借阅记录查询功能，补充接口测试。未提供可核验的效果指标。",
  "source": "虚构示例，仅演示格式"
}
```

实际资料中的 `source` 可写“本人于某日确认”或“private/sources/resume.md 的某条项目记录”，但应填入真正存在的来源。路径只是来源指针，不证明事实真实；不要引用不存在的文件来补齐格式。

日期只到年月时保留年月；网站要求具体日则交接确认。仍在进行中的经历应明确标注，不能自行猜测结束日期。团队指标必须说明归属，不自动变成个人提升。

研究记录可增加 `type`、`publication_status`、`status_as_of`、`author_role`、`author_order`、`venue` 和 `contribution`。保留“撰写中、预印本、已投稿、在审、录用、发表”的真实区别；作者信息缺失就标未知，不能默认第一作者。论文、专利和标准各按真实类型呈现。

## 缺失值的语义

`null` 表示没有可直接使用的值，`[]` 表示当前没有条目；二者都不能单独证明“本人没有这项经历”。建议通过 `field_metadata` 解释：

```json
{
  "education": [],
  "awards": [],
  "field_metadata": {
    "education": {"status": "unknown", "note": "尚未整理"},
    "awards": {"status": "confirmed_none", "note": "本人明确确认没有可填奖项"},
    "basic.phone": {"status": "withheld", "note": "本次不提供"}
  }
}
```

| 状态 | 含义 | 处理方式 |
|---|---|---|
| `unknown` | 尚未提供或没有可靠信息 | 先查已提供正文，仍缺失则询问 |
| `pending_confirmation` | 有候选值但未确认 | 不当作确定值填写 |
| `confirmed_none` | 本人明确确认没有 | 在语义匹配的字段中才可填“无” |
| `not_applicable` | 对此人或此申请不适用 | 按网站真实选项处理 |
| `withheld` | 本人选择不披露 | 不从其他来源重新补回 |

这些是建议状态词，不是强制枚举；已有 JSON 的明确语义可以保留。若要记录已确认值，可使用 `confirmed` 并附来源。记录级状态可按稳定 record_id 标识，但需在资料中写清路径规则，不把自然语言路径冒充脚本支持的 JSON Pointer。

## 从已有履历迁移

1. 先完整盘点现有材料，把不同经历分开，保留原始来源。
2. 提取事实正文，未知值和冲突单列；不要让模型自动润色成更强的成果。
3. 自行确认日期、身份、研究状态、奖项范围和指标归属。
4. 保留稳定记录 ID；已有正文可直接复用，不必每次投递重写。
5. 根据个人更正更新 JSON；单个公司曾填写的个人选择不自动成为其他公司的答案。

可选原始资料库用于补充真正缺失、过时或冲突的信息。完整 JSON 已能说明事实时，不要求每次重读所有证明材料。

## 隐私和数据流

- 个人 JSON 与运行资料放在公开仓库之外；运行计划和快照也可能包含联系方式和履历正文。
- 证件号码由本人在网站输入；密码、Cookie、令牌、验证码不进入资料文件或工具日志。
- agent 读取本地资料可能经宿主发送给模型服务；填写内容会进入招聘网站。不要把“文件在本地”解释为“全过程离线”。
- 仓库脚本不内置上传或遥测服务，但宿主、浏览器工具与网站各有自己的数据处理方式。
- 提问或提交 issue 时使用虚构记录，不上传个人 JSON。`.gitignore` 不会清除已提交的 Git 历史，也不替代访问权限。
