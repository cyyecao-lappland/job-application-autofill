# 岗位筛选：完整盘点，选择呈现

## 从实际 JD 得到排序依据

记录职位、公司、JD 来源及读取时间。提取少量带稳定编号的要求（如 R1 Agent 训练、R2 检索、R3 服务部署），分别标核心职责、硬性条件或加分项。引用 JD 原文短句，保留“必需”和“优先”的区别。不能把职位名推测出来的技能写成 JD 原文。

JD 无法读取时，优先找该职位的官方说明；仍不可得就标明依据不足，继续基础事实填写，必要时一次询问用户提供 JD。不能声称已完成针对性排序。

## 履历盘点与取舍

优先读取 SKILL.md 指定的完整资料 JSON，按教育、实习、项目、论文、专利/标准、奖项、校园经历、技能证书列 inventory。JSON 已有正文、贡献和状态时直接复用，不为了排序逐篇重读原始文件。仅在 JSON 不可用、类别未收录、状态冲突或疑似遗漏时定点查履历库索引和源条目；用户的排除与呈现策略先于 JD 排序。

每项至少保留 `id`、名称、类别、source。与其他条目实际是同一工作时可以关联或合并，不能重复宣传成两个独立成果。填写选择依据：与核心职责的直接关系、本人贡献是否明确、证据是否充分、是否补充已有内容未证明的能力，以及网站字数/条数约束。

| 优先级 | 依据 | 默认呈现 |
|---|---|---|
| P0 | 直接证明核心职责或硬性能力 | 优先、较详细：问题、个人行动、可信成果 |
| P1 | 补充相关工程、交付、研究能力 | 择优简写，避免重复证明 |
| P2 | 弱相关、重复或证据不足以突出 | 默认省略并记录理由 |

不按关键词个数、名气、篇幅机械打分。不设每个网站都一样的项目数量；在实际容量内以相关且互补为准。不要为了填满可选栏目补入大量 P2 内容。基本时间线和网站明确要求的全量信息单独遵守。

## 内容完整性约束

覆盖表必须包含 inventory 中每个 id，且只能出现一次；允许 `include`、`brief`、`merge`、`omit-relevance`、`omit-capacity`、`manual`、`missing-fact`、`no-field`。include/brief/merge 指明落到哪些操作 id；merge 标明合并目标 id，不得自指或循环；省略/手动/缺事实写原因。不能把没有准备答案伪装成控件失败。

每条 P0/P1 应关联真实 JD 要求编号；必填基本信息可用 `mandatory: true` 而不强行关联 JD。没有找到对应能力时写“履历暂无依据”，不能硬改经历来满足要求。

所选实习/项目检查身份归属、时间、问题、个人贡献、关键成果；压缩的是篇幅，不是把个人贡献全部删掉。项目必须归属来源确认的任职或研究经历；某个任务的指标不能移用于另一任务。论文在写、在投、在审、录用等状态必须重新核对当前来源，不沿用旧试验中的状态。

执行前在本地确认：每个 inventory 项有决策；每个被选内容有操作去向；每个修改值有事实来源；P0 无法呈现的原因已醒目标记。无需增加一轮浏览器调用，也不默认要求用户每次审整张表。

交接时展示少量重点和主动省略理由即可，完整覆盖表留在本地。结果不能只说“填了 40 个字段”，还要说明核心经历有没有呈现。
